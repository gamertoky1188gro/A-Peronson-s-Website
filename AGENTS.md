# AGENTS.md — Problems & Fixes

## 34. The AI reply was escaped three times, and new lines were flattened (Owner)

- **Problem:** two bugs in the clarifying-chat path, both invisible to the unit suite (all providers were mocked) and only surfaced by a live browser session. (a) The buyer saw literal `you&#39;re` in the assistant bubble (and in the case header): the model text was entity-escaped in **provider → clarification service → controller** before persistence, so the decode pass left `&#39;` stale. (b) The `Chips:`/`Check:` markdown the intake prompt teaches never rendered as buttons: `sanitizeString` collapsed every newline to a space, so the per-line marker parser never matched.
- **Fix:** the whole intake path is raw now — the opencode provider returns the raw turn, `caseConversationService` stores with a boundPlain trim (newlines preserved, no entity encoding), the controller reply path binds the same way, and `setCaseSubject` stores a raw single-line title. React escapes at render, which is the correct single place.
- **Gotchas:**
  - **One escape, one decode.** `escapeHtml` produces exactly the set `decodeStoredText` reverses; any other person adding `sanitizeString` upstream of a React-rendered surface on the assistant path re-introduces stale entities.
  - **`sanitizeString` collapses newlines.** Anything parsed line-by-line (Chips/Check tables) is silently destroyed by any of its three callers.
  - **Biome bans control characters in regex literals, escapes included.** Literal `\u{0}-\u{1f}` ranges trip `noControlCharactersInRegex` — the fix was to not strip at all rather than fight the rule (React escapes at render).
- **Also fixed this round:** the context meter froze at 0.0% because the intake clarification never emitted `support.case.usage`. `makeClarificationProvider` now emits `role:"intake"` usage SSE from `waitForAssistantTurn`'s `onUsage`; the meter showed `13.0% · 136,528 / 1,048,576 tokens` after two turns.

## 32. The crash logger deleted the file it was writing (Owner)

- **Problem:** commits bounced on `tests/unit/server-auth-hardening.test.js` — "records are written synchronously, once per error, and rotated" failed intermittently under the full suite and passed standalone. It was documented as an unexplained flake. The cause was a real bug in `server/utils/crashReporter.js`: the rotation prefix `"crash-history."` **also matches the live file** `crash-history.jsonl`, so the file being appended to was a prune candidate. The prune kept the `maxFiles` newest by mtime — and when the live file's mtime tied with a rotated copy (same millisecond, and a crash burst writes several records per millisecond), the live file was the one deleted. The history was lost, and the test failed. The daily log had the same hole: the prefix was the literal `"crash-2"`, which only matches because the year starts with a 2. **Measured:** with the old reporter the test failed **6 of 8** runs; with the fix it passed **8 of 8**.
- **Fix:** `pruneOldFiles` now takes the set of **active** file names and skips them, so a file that is being written is never a candidate. The daily prefix is the **day** (`crash-${day}`), not the year digit, so it keeps matching whatever the year is. The test now counts **rotated** copies (`name.startsWith("crash-history.") && name !== "crash-history.jsonl"`), which is what its own comment always said, and a new test asserts the live file survives a six-record burst and still holds the newest record.
- **Gotchas:**
  - **A rotation prefix must never match the live file.** The prefix is a *pattern for rotated copies*; the live file has to be excluded explicitly, because a name that starts with the prefix is not a rotated copy.
  - **mtime ties decide the victim.** `sort((a, b) => b.mtime - a.mtime)` is stable, so when two files share a millisecond the readdir order decides which one is pruned. A burst of writes in one millisecond is the normal case, not the edge case.
  - **The old test was counting the live file as a rotated copy.** `files.filter((n) => n.startsWith("crash-history."))` includes `crash-history.jsonl`, so the assertion `≤ 2` was really "the live file plus one rotated copy" — it passed only while the live file happened to be the newest. Fixing the reporter without fixing the count would have failed the suite for a different reason.
  - **Do not "fix" this by weakening the gate.** The old instruction was to retry the commit. The retry hid a data-loss bug in the crash logger; the fix is in the reporter.

## 31. The assistant killed a healthy opencode server and then blamed the model (Owner)

- **Problem:** the chat assistant never answered through opencode. It spawned the isolated server, which printed `server listening`, and then **killed it twenty seconds later** — because its readiness probe was `GET /api/global/health`, a route the v2 server does not implement at all. The probe answered 404 every time, so `response.ok` was false, the poll could never succeed, and a perfectly healthy server was treated as a failed start. The assistant then fell through to its second provider, that failed too, and the client was handed `forward_to_agent` instead of an answer. Once the server *was* reached, the answer still did not arrive: the model turn takes longer than the 45-second global request budget, so `requestLogger` returned `504 {"error":"Request timeout"}` for a turn that was about to succeed.
- **Fix:** the readiness probe is now `GET /api/model` — the route the v2 SDK's `model.list()` calls, and the only one that answers once the location has finished activating its plugins. The window is `OPENCODE_READY_TIMEOUT_MS` (default **180 s**, the same window the investigation runtime already used, 1 s poll) instead of a round 20 s. `OPENCODE_ENABLED` is compared case-insensitively by one `isOpencodeDisabled()` helper, so the availability check and the spawn decision can no longer disagree. The configured model was also one the server does not offer (see the first gotcha), so the default and `render.yaml` now name `minimax-m3.1-flash-free`. And `requestLogger` gives the AI routes (`/api/assistant/`, `/api/ai/`) `AI_REQUEST_TIMEOUT_MS` (default **180 s**) — never *less* than the global default, so a deliberately small `REQUEST_TIMEOUT_MS` still applies.
- **Gotchas:**
  - **The configured model was not one the server offers.** `OPENCODE_MODEL_ID` named `opencode/deepseek-v4-flash-free`. `opencode models` lists the free tier as `deepseek-v4.1-flash-free`, `mimo-v2.6-flash-free`, `glm-5.3-flash-free`, `minimax-m3.1-flash-free`, `beam-free`, `flint-40b-free`, `nemotron-3-ultra-free`, `nemotron-3.5-lightning-free`, `nemotron-3.5-super-vl-free` and `big-pickle` — there is no `deepseek-v4-flash-free`. A session pinned to a model id the provider does not have can never take a turn, so a correct probe alone would still have produced a timeout. The code default (`server/services/assistantService.js`) and both `render.yaml` keys now name `minimax-m3.1-flash-free`, the model that was measured answering when the others returned `429 provider.quota`.
  - **`render.yaml` declared the model twice, and the code read neither name directly.** `OPENCODE_MODEL_ID` is the one `aiConfig.opencode.modelID` reads; `OPENCODE_MODEL` is read by nothing in the server, so it silently kept the old, nonexistent id. Both now carry the same value.
  - **A port that accepts connections is not a server that is ready.** Measured on a cold start: the port answered `/` at ~15 s, `/api/config` at ~16 s, `/api/provider` at ~16 s, and `/api/model` only at ~20 s. On a settled server, `/api/model` answered in ~2 s. `/api/config` answers *while* the server is still initializing, so it is not a readiness signal either.
  - **`/api/global/health` does not exist on the v2 server** (404 with and without a trailing slash, authenticated). The 20-second deadline was therefore not a timeout at all — it was a guarantee.
  - **Neither 20 s nor 45 s was ever measured.** The assistant's own init test (`"Hello"`) took **34 s** on a free model; an ask that also builds context is longer. A model turn needs a budget in minutes, not seconds.
  - **A 504 is not a model failure.** The turn keeps running server-side after `res.status(504)`; the client simply never sees the answer. The AI budget is a ceiling above the provider's own 120 s turn timeout, not a replacement for it.
  - **The probe scripts are the evidence, and they are disposable.** `/api/global/health`, `/api/health` and `/api/model` were compared against a real spawned server; the same script showed `/api/model` ready at 20 s. The fix was then verified through the assistant's own `ensureOpencodeServer()` — it returned a real session in **~15 s** — and end to end over HTTP: `POST /api/assistant/ask` ("Reply with exactly the word: opencode-works") answered **`200` in 68 s** with `matched_answer: "opencode-works"`, where before it returned `forward_to_agent` or `504`.

## 30. The escalation paged the staff for a missing feature (Owner)

- **Problem:** a live run produced a **CONFIRMED** finding that was entirely correct, and the escalation path paged the owner/admin over it. The finding read: *"The only DELETE route in documentRoutes.js is `DELETE /api/documents/:documentId`, which is a **hard delete** of a Document row and **is not called from ContractVault**."* The classifier matched the phrase `hard delete` and returned `data_loss`, so a case about a **missing Delete button** escalated as a **data-loss incident**. The finding says the opposite of an incident — it says the destructive route is never reached. Nobody was paged about a data-loss event; they were paged about a missing feature.
- **Fix:** the classifier now refuses a finding that **denies** the harm. `HARM_DENIAL_RE` names the ways a finding says the harm does not happen — *is not called, never called, no route, cannot delete, does nothing* — and a finding containing one of them is describing a **capability**, not reporting an incident. The guard is deliberately narrow, so a real incident (*"the archive endpoint permanently deletes every contract"*) still escalates. Two gaps in the classifier were closed at the same time: the word forms it was missing (*deletes*, *hard-deletes*, *has no authorization check*), and the order — **security is now tested before data loss**, because a missing access control is the *defect* and the deletion is only its *consequence*.
- **Gotchas:**
  - **"Any authenticated user can delete another user's contract" matches BOTH categories.** It is an access-control defect; data loss is its effect. The defect is the more precise answer.
  - **The benign complaint contains the harmful words.** *"The delete button on the Contract Vault page does nothing when clicked"* names a delete and a contract, so a proximity match reads it as data loss. `does nothing` is a denial of the harm and belongs in the guard.
  - **A text classifier that pages people must be biased towards silence.** A false positive costs a human being's attention; a false negative leaves the finding in the report and the console, where it is still seen. The asymmetric cost is why the guard suppresses on ANY denial marker.
  - **An explicit `category` on the finding is trusted and bypasses the guard** — the agent is telling us what it is. The guard only applies to the text path, which is the guessing path.

## 29. The free model chain was never used for fallback, and a refusal looked like a JSON bug (Owner)

- **Problem:** the third live run died from a quota, and every part of it was invisible. The free tier's quota is **per model**: measured against a live runtime, `deepseek-v4.1-flash-free`, `mimo-v2.6-flash-free` and `glm-5.3-flash-free` all answered HTTP 429 `provider.quota` while `minimax-m3.1-flash-free` answered normally. The queue picked the first **available** model and stopped — so one exhausted model killed every role after it (`repo`, `research` and `verify` each failed in **3–5 seconds with zero tool calls**). The chain of ten free models existed precisely for this and was used only to *pick*, never to *fall back*. Worse, the refusal arrived as `finish: "error"` with `error: { type: "provider.quota", status: 429 }` and **no content at all**, and the turn reader threw the error away — so a 429 was reported as *"the agent did not answer with JSON"*.
- **Fix:** the chain is now a fallback chain. A role that a model **refused**, or that answered with something the parser could not read, is retried on the next model of the chain. A **timeout is not retried** — the model was working, it just needed longer, and retrying would double the wall clock for the same result. The refusal is now surfaced by name (`errorKind: "model_refused"`, with the provider's message and status) instead of being reported as a parsing fault.
- **Gotchas:**
  - **"Available" and "working" are different questions.** `listAvailableModels` says the server *offers* the model; it says nothing about whether the account has quota left for it.
  - **A refusal produces no content, so it is indistinguishable from silence unless the error is read.** The error lives on the *message*, not in the content — `message.error` is where the provider's reason is.
  - **A model that answers with prose is worth retrying too.** The models differ in how well they follow the JSON contract, and a preamble ("I'll start by exploring the repository structure…") with no JSON is a different model answering, not a broken one.
  - **A model that answers with prose is worth retrying too — but first, ask it again.** The commonest miss is not a refusal but an *explanation*: "Based on my investigation, I can now provide a" and then prose, or a preamble and no JSON. That model has usually **already done the work** — the answer is one formatting step away and the session still holds the context. So the queue first sends **one more turn in the same session** ("reply with ONLY the JSON object"), which costs a single call and does not re-run the investigation, and only then falls back to the next model. In a live run this turned two failed roles into completed ones with real findings.
  - **A fallback must not erase the diagnostics.** The row used to be OVERWRITTEN by each attempt, so the reason the *first* model failed was gone by the time anyone looked. Every attempt's failure is now kept on the row.

## 28. Never kill a process by its name (Owner)

- **Problem:** cleaning up the `opencode serve` runtimes that a killed investigation leaves behind, the cleanup was `Get-Process -Name opencode | Where-Object { StartTime -gt … } | Kill()`. That matches **every** opencode process on the machine — including the operator's own session. It killed the operator's session three times, and each time the whole environment appeared to "restart": the harness died, took the server and the running investigation with it, and the in-flight work was lost. The command was meant to remove four orphans and instead removed the person using the computer.
- **Fix:** the cleanup was abandoned. The investigation runtime already stops its own child in a `finally`, so a graceful shutdown leaves nothing behind; the orphans only appear when the server is `SIGKILL`ed, and they are idle servers on random ports that cost some memory and nothing else. If they do need removing, identify them by **parent PID** (`Get-CimInstance Win32_Process -Filter "Name = 'opencode.exe'"` shows `ParentProcessId`) or by their command line — never by name.
- **Gotchas:**
  - **`Get-Process -Name X | Kill()` is not "cleanup", it is a machine-wide kill.** There is no scoping in it. Any process whose name matches is a target.
  - **A name match is not an identity.** Three different things on this machine are called `opencode`: the operator's session launcher, the v2 CLI binary it spawns, and the investigation runtime. Only the parent PID tells them apart.
  - **The symptom pointed away from the cause.** Every restart looked like the environment crashing. It was this command, running inside the thing it was killing.
  - **The investigation's own cleanup was never the problem.** `runtime.stop()` in the `finally` handles the graceful path, and the live run confirmed it: a normal completion left **zero** orphaned runtimes.

## 27. The investigation had no stopping condition, and the reader ended turns mid-thought (Owner)

- **Problem:** three defects that the first two live end-to-end runs found and that **832 unit tests and the live spike could not have found** — every unit test mocks the runtime, and the spike's prompt is trivial enough to answer in seconds. (a) The prompts said *"Read the repository"*, *"Trace the path end to end"*, *"Open the cited files yourself"* and nothing else: an open-ended search with no budget. A free model takes that literally — the `lead` role made **67 read-only tool calls in ten minutes** and was still going when the clock ran out, so the turn was cut off before it wrote its answer and all that work was lost. (b) The turn reader could end a turn while the model was still **thinking**: the v2 message list does not change between tool calls, so the stability heuristic fired during a generation pause and declared the turn finished with **no text at all** — which the JSON parser then reported as a parsing failure. (c) The client's evidence was handed to the agent as a **public** path (`/uploads/support/x.png`), but the agent's read tool is rooted at the repository, so that path resolves to nothing: the agent burned a tool call on `File not found` and never saw the screenshot it was asked about.
- **Fix:** (a) every role now gets a tool-call budget — `INVESTIGATION_AGENT_TOOL_BUDGET`, default 24 — and is told to stop and report when it is spent, with the rest in `limitations`; the timeout is now the backstop rather than the mechanism. (b) the reader refuses to settle on the stability window while the newest assistant message still says it is going to call another tool (`finish === "tool-calls"`). (c) the agent gets the **absolute** path, plus a note that a binary image may not be readable and that guessing at its contents is not allowed.
- **Gotchas:**
  - **A timeout is a symptom; a budget is the cure.** Raising 180 s to 600 s only moved the wall. The agent did not need more time — it needed to be told to stop.
  - **"Roughly N tool calls" beats "at most N".** A model counts badly. The instruction that actually makes it stop is the second one: *"a search that has not found the answer within your budget IS a finding"*.
  - **The v2 message list is silent while a model thinks.** Anything that infers progress from "the list stopped changing" is inferring the model's thinking time, not its idleness. The authoritative signal is `finish`.
  - **`finish` is the whole contract, and it arrives late.** Measured against a live runtime: a reply carries `finish: undefined` at 2s and only settles to `"stop"` at 16s. **`undefined`/`null` means the model is STILL WRITING that message** — it is in the list before it has any content. `"tool-calls"` means another tool is coming, `"stop"` means that was the last message, and an `idle` message means the server says the turn is over. Treating "no finish" as "finished" is what abandoned turns mid-generation.
  - **A streamed answer grows, so its LENGTH belongs in the change signature.** The signature used to count parts and tool statuses, so a long answer looked exactly like a stalled turn.
  - **Name every way a turn can end.** `finished`, `timedOut` (the clock) and `wedged` (the model stopped making progress) are three different faults, and they were all being reported as "the agent did not answer with JSON" - which sent the operator hunting for a parsing bug that did not exist.
  - **The agent's file tool is rooted at the repository, but the upload API speaks public paths.** `/uploads/...` is for HTTP clients; a tool that opens files wants an absolute path. The two vocabularies have to be translated at the boundary, not in the prompt.

## 26. Every investigation role died at 180s, and the failure was reported as a JSON bug (Owner)

- **Problem:** the first live end-to-end run of the support-investigation portal produced **no findings at all**, and the reason was invisible. All four specialist roles failed with `The agent did not answer with JSON (empty_text). Raw answer:` — with an *empty* raw answer. The cause was not the model, the prompt, the JSON contract or the free tier: `investigationQueue.js` capped an agent turn at `AGENT_TIMEOUT_MS = 180_000`, and `opencodeTurns.js` had a matching `DEFAULT_TIMEOUT_MS = 180_000`. A codebase investigation is not a one-shot question — the agent reads a file, greps, reads three more, and only then writes its answer — so the `lead` role was cut off **with 17 COMPLETED read-only tool calls and no answer at all**, at 11:38:34, exactly 182 s after it started. The `code` role died the same way one second later. Every role failed; only `verify` completed, because it had nothing to verify and answered at once.
- **Fix:** two changes, and the second is the one that matters. The turn reader now records **why** the loop ended: `waitForAssistantTurn` returns `timedOut: true` when the deadline expires without the turn settling, and `runAgentPrompt` turns that into a distinct error — *"The agent did not finish within Ns. It had made M read-only tool call(s) and was still working."* — instead of returning an empty string that the JSON parser then blamed. The timeout itself is now `INVESTIGATION_AGENT_TIMEOUT_MS`, defaulting to **600 000 ms** with a 60 s floor, because the queue's constant was the real limit.
- **Gotchas:**
  - **A deadline that expires silently is indistinguishable from an agent that answered with nothing.** `while (Date.now() < deadline)` used to fall out of the loop with no marker, so the caller saw `""` and reported a *parsing* failure. The operator would have gone looking for a JSON bug that did not exist. A timeout must be **named**.
  - **The tool calls an agent made before it was cut off are evidence, and they are kept.** The error says how many read-only calls completed. "It had made 17 tool calls and was still working" is a diagnosable fact; "empty_text" is not.
  - **832 unit tests and the live spike could not have found this.** Every unit test mocks the runtime, and the spike's prompt is trivial enough to answer in seconds. Only a real investigation against a real codebase takes long enough to hit the wall. The first end-to-end run found it in one pass.
  - **The 180 s figure was never a measured number.** It was a round default that had nothing to do with how long an agent needs. A codebase investigation on a *free* model is slower than a paid one, so the tier that makes the feature affordable is the tier that breaks the timeout.
  - **The report was honest about it.** The renderer printed *"This report is INCOMPLETE. 4 of 5 investigation run(s) failed … A failed run is not a clean result: it did not look for anything, so its silence is not an answer."* and the case still reached `completed`. That is the behaviour the spec asked for, and it is what made the defect diagnosable at all.
  - **The email in that run recorded `failed`, not `sent`**, because `notifications.email.enabled` is `false` in the admin config and `emailService` reports `logged_disabled`. The honest verdict is the whole point of Task 6; a green `sent` would have been the bug.

## 25. The support portal's pieces existed but were never connected (Owner)

- **Problem:** five parts of the support-investigation portal were built in parallel and merged with zero conflicts — but nothing joined them up. The investigation queue ran the five read-only agents and wrote `SupportInvestigation` rows, and then **nothing called** `buildReport`, `deliverReport` or `escalateIfNeeded`. The investigation ran and produced no report, no email, and no escalation. Alongside that: `POST /support/cases/:caseId/confirm` set `status: "investigating"` unconditionally, so the client's post-report "Confirm this is accurate" button **restarted a finished investigation and overwrote its summary**; the report email linked to `/admin?case=<id>` while the console never read that parameter, so the owner's "open the case" link went nowhere; `render.yaml` declared no `APP_BASE_URL`, so the emailed link fell back to `localhost:4000` in production; the optional `category` on a finding was dropped by `normalizeFindings` and again by `applyVerification`, leaving escalation to guess from the text; and the admin escalate/rerun routes had no test at all.
- **Fix:** the queue now owns the end-to-end pipeline — it builds the report, persists it, calls `deliverReport`, calls `escalateIfNeeded` **independently of the email** (a confirmed data-loss finding must escalate even if the mail fails), and drives the case to `completed` or `failed`. `confirm` is idempotent: it only moves a case that is still `collecting`. The console reads `?case=` and auto-selects that case, and `APP_BASE_URL` is declared in `render.yaml` via `fromService`, with `RENDER_EXTERNAL_URL` added to the fallback chain. `category` is preserved through `normalizeFindings` and `applyVerification`.
- **Gotchas:**
  - **The final finding set lives on the `verify` row, not on a concatenation.** The four specialist rows hold the per-agent log; the `verify` row holds the accumulated set with verification applied. Reading every row's `findings` double-counts. The report renderer keys findings by `detail`+`confidence`+`evidence` and counts each once.
  - **The signed URL is the credential.** `/api/files/content` is deliberately unauthenticated so `window.open`/`<img>`/downloads work without an `Authorization` header, which means a signed URL is a **bearer credential** — presenting it verbatim works until it expires. `uid` and the resolved path are bound into the HMAC, so a URL cannot be re-pointed, but it can be forwarded. Do not put a signed URL in a log.
  - **`POST /confirm` carries two intents** ("start the investigation" and "this is accurate"). The route is idempotent rather than two routes, because there is no column for "the client confirmed" and adding one is a schema change.
  - **`APP_BASE_URL` must be a public URL.** `VITE_BASE_URL` is `/` because the frontend is served through a proxy; it is not the base for the emailed link.
  - **The migration is not applied to any database.** `prisma migrate dev` would have offered to reset the shared Aiven instance, so the SQL was generated offline with `migrate diff` and is applied by `render.yaml`'s `migrate deploy`. Until it is applied, a live smoke test fails with `P2021: the table public.support_cases does not exist`.

## 24. The signed-file gate had three residual holes (Owner)

- **Problem (a) — the media lost its fade.** The fix wave changed `className={className}` to `class={className}` in `src/components/chat/SignedMedia.jsx`. React 19 does render `class` on a DOM element (and warns about it — once, see the end of this sentence), so the `<video>` kept working, but `LazyImage` reads `className` and spreads everything else onto the `<img>`, so `class` fell through `...rest` and landed on the `<img>` as a **second** class attribute, replacing the `transition-opacity duration-200 opacity-0/100` classes LazyImage sets. The fade was gone, and React logged "Invalid DOM property `class`. Did you mean `className`?" **once** — React deduplicates that warning per property name for the life of the React module, so only the FIRST DOM element that receives a `class` prop reports it, whichever element that is: measured in isolation, `<img>`, `<video>` and `<div>` each warn exactly once, and three `<img>`s in a row still warn once.
- **Problem (b) — the `/sign` budget was too tight, and a 429 was silent.** The client signed **one path per request**, so a chat thread with fifty images was fifty requests against a 60/minute per-user budget, and every preview modal spent another one asking whether a document may be handed to a third party. Worse, `signPaths` caught every failure and returned `{}`, so a rate-limited sign and a refused sign were indistinguishable: the thumbnail or the download simply did not appear, with nothing on screen to say why.
- **Problem (c) — a name collision left a file unreachable.** The registry pass that adopts files already on disk (`ensureDocumentRowsForExistingFiles`, `server/services/uploadsService.js`) matched by **basename**, so `a.pdf` in `chat/` and `a.pdf` in `contracts/` meant the second file never got a row — and a file with no row is unreachable for everyone (item 23).
- **Fix:**
  - (a) `className` restored in `SignedMedia.jsx`.
  - (b) The client **batches** sign requests (`signEntry` in `src/lib/signedFile.js`): everything asked for in the same turn goes in one request, chunked at the server's own 50-path cap. A 429 is reported as `SIGN_RATE_LIMITED` instead of being swallowed, the client backs off for a second before its next request, and the surfaces say so. The server's request budget went to 300/minute and a **path budget** (1500 paths/minute) was added, so the headroom is paid for in requests and not in server load.
  - (c) The registry now keys files by their **normalised public path**, not their name.
- **Gotchas:**
  - **The path budget is the one that bounds the work.** A request may carry 50 paths and every path costs a database round trip inside the authorization resolver, so a request cap alone does not bound the server's load: 300 requests x 50 paths is 15,000 authorizations a minute. `createUnitBudget` (`server/middleware/rateLimiter.js`) counts paths separately for that reason, and 1500 paths a minute is half the work the old 60-request cap allowed.
  - **Both budgets fail closed.** Over budget is a 429, never an allow-through, and the client never falls back to the raw path.
  - **The client's sign requests are queued on a microtask**, so a sign is one microtask later than it used to be. Anything that asserts "exactly one request so far" has to allow for that (`tests/unit/frontend-signed-file.test.js`).
  - **`useSignedSrcState` is the form that reports a failure**; `useSignedSrc` still returns a string and cannot tell a pending sign from a failed one. A surface that shows nothing on failure has to use the state form, or the failure is invisible again.
  - **The registry's key is the full path.** A file adopted under a basename that belongs to another directory is unreachable for everyone — the same failure mode as a missing row.
  - **A sign failure has ONE shape: the server's own `{ error, status }`.** `useSignedSrcState` used to rename it to `{ reason, status }` while `describeSignFailure` reads `error`, so the reason was dropped at the boundary: the chat thumbnail and the modal's sign banner — the two surfaces driven by the hook — showed the generic "could not be loaded" for a rate limit and for a refusal alike, which is the very confusion the failure half exists to remove. The hook now reports the entry unchanged, and `describeSignFailure` is the only place a failure is understood. A surface that invents its own field name for the reason silently loses it.

## 23. The upload access control's authorization key was never created (Owner)

- **Problem:** the whole branch keyed file authorization on a `Document` row, but the only producer of those rows for `chat/`, `calls/` and `search/` was the AI-moderation backfill — and that is disabled in the deployed configuration (`AI_HARAM_ANALYTICS_ENABLED=false` in `render.yaml` and `.env`) and only ever covered image/video. A chat `.pdf`/`.txt`/`.html` never got a row regardless. `authorizeFilePath` answers `not_found` for a path no row anchors (`fileAccessService.js`), so every chat attachment, every call recording and every search image was unreadable by *everyone*, the uploader included. The static mount 404s the gated prefixes, so there was no fallback.
- **Fix:** the row is written at **write time**, where the ownership facts exist: `server/services/privateDocumentService.js` (`recordPrivateUpload`) is called by the chat upload (`server/controllers/messageController.js`), the recording upload (`server/controllers/callSessionController.js`) and the search-image upload (`server/controllers/searchController.js`). The registry pass that adopts files already on disk (`ensureDocumentRowsForExistingFiles`, `server/services/uploadsService.js`) is split out of the moderation scanner, so it runs whatever the flag says and covers every file type, not just media.
- **Gotchas:**
  - **A file with no `Document` row is not public — it is unreachable.** That is the fail-closed direction, and it is why row creation cannot depend on a feature flag. Do not "fix" a missing row by re-enabling the moderation scan.
  - **A call recording is authorized against the session that owns it**, named by `entity_id` — never against `recording_url`. That column is caller-supplied (`PATCH /api/calls/:callId/recording` is `requireAuth` only and stores any string) and `markRecording` only asks whether the caller is a participant of *their own* session, so a url as the anchor let a caller point their own session at any recording path and then be "a participant of a session whose recording is that file".
  - **`search/` is modelled, not un-gated.** The upload route (`POST /api/search/image`) is `requireAuth`, so the uploader is a real party to the file: the row is `entity_type: "search_image"`, authorized on `uploaded_by` and on the path being under `/uploads/search/`. The old scanner's `uploads` type lands in the resolver's default branch, which denies every non-admin.
  - **`POST /api/documents/url` is now `requireAuth` + `allowRoles("owner","admin")`.** It is not in the original spec or plan — it is an API change, recorded in the design spec (§6.4a), in the plan's Task 3 addendum, and in `docs/decisions/`. `ensureAllowedUrl` accepts any `/uploads/...` path, so that route was the forgery vector; `tests/unit/server-file-access.test.js` asserts the role restriction, so widening it is a deliberate edit to a test.
  - **`UPLOADS_SIGNING_SECRET` is required at boot.** It is in `REQUIRED_ENV_VARS` (`server/utils/envValidation.js`), declared in `render.yaml` with `generateValue: true`, and refused below 32 characters. Unset or short, the server exits instead of booting into a state where every private file is unreachable with no signal.
  - **The client keeps no copy of the server's gated-prefix list.** `/api/files/sign` answers `thirdPartySafe` per path, and the server returns the `ttlMs` it used. A client-side copy of either drifts silently, and the consequence of the prefix list drifting is a private document's signed url reaching `view.officeapps.live.com`.
  - **The 208 orphan contract PDFs are admin-only and stay that way** — `uploaded_by: "system"`, no parties, no `contract_number`. There is no claim path yet; the rollout note is `docs/rollout/2026-10-18-upload-access-control-rollout.md`.

## 22. Private uploads were world-readable (Owner)

- **Problem:** `server/server.js` mounted all of `server/uploads/` through `express.static` with no auth, so every contract PDF, chat attachment, call recording and search upload was fetchable by anyone holding the URL. Filenames are `${Date.now()}-<sanitized basename>` (`server/routes/messageRoutes.js:108`) — guessable, permanent, never expiring. Nothing wrote a `DocumentView` on the way in, so there was no audit trail either.
- **Root cause:** One blanket static mount served the public and private trees together. `chatUploadsRoot` was created at `server/server.js:283` and only ever `mkdir`'d — never served. `server/routes/uploadsRoutes.js` exposes listing/stats/delete only, never bytes. `DocumentView` modelled access, but the static mount bypassed it, so the model was never enforced and never recorded.
- **Fix:** The four private prefixes (`chat/`, `contracts/`, `calls/`, `search/`) are now reachable only through short-lived HMAC URLs minted by `POST /api/files/sign` (`server/routes/fileAccessRoutes.js:38`) and authorized through `Document.entity_type` (`server/services/fileAccessService.js:176`). `GET /api/files/content` (`fileAccessRoutes.js:90`) verifies the signature, re-resolves both ends through `fs.realpath` so a symlink planted inside the tree cannot escape the root, records a `DocumentView` for contract PDFs (`fileAccessRoutes.js:120`), and serves with `Cache-Control: private, no-store` instead of Express's default `public, max-age=0` (`fileAccessRoutes.js:129`). The static mount 404s gated prefixes via `server/utils/gatedStaticGuard.js`, mounted at `server/server.js:315` immediately in front of `express.static` (`server/server.js:316`) so a later mount rearrangement cannot silently reopen them. `feed/`, `profile/` and root CMS assets stay public — the `/share/:entityType/:entityId` route (`server/routes/feedRoutes.js:150`) hands out post payloads that reference them. Client side: `src/lib/signedFile.js` (`signOne` / `signAndOpen` / `signAndDownload`).
- **Fix (emailService, same branch):** the four log-only branches (`logged_disabled`, `logged_no_smtp`, `logged_no_gmail`, `logged_unsupported`) reported `ok: true` while sending nothing; they now return `ok: false` (`server/services/emailService.js:115,130,143,155`). `describeEmailTestOutcome` (`src/pages/AdminPanel.helpers.js:1005`, used at `src/pages/AdminPanel.jsx:2293`) reads that flag, so the admin notice distinguishes "Test email sent." from "Test email not delivered (<status>)" instead of claiming a send that never happened.
- **Gotchas:**
  - **The guard is its own module, not inline in `server.js`.** The 404 logic lives in `server/utils/gatedStaticGuard.js`; `server.js` only mounts it.
  - **Sign the `path.resolve`d absolute path, not the query parameter.** The HMAC input is `JSON.stringify([absPath, uid, exp])` (`server/utils/signedFileUrl.js:64`) with `absPath` the resolved absolute path. Signing the raw `?path=` value would let `?file=../../.env` sign cleanly.
  - **Decode, then normalize, then classify.** `serve-static`/`send` percent-decode and textually normalize the path *before* reading the file, while `req.path` at a mounted middleware is still encoded — classifying `req.path` as-is leaves the two sides out of step and lets `/uploads/%63ontracts/x.pdf`, `/uploads/./contracts/x.pdf` and `/uploads/feed/../contracts/x.pdf` walk past. The guard decodes (`gatedStaticGuard.js:109`), folds `\` to `/`, collapses separators and `path.posix.normalize`s (`:123-124`) before classifying.
  - **On NTFS, `fs.realpath` must be the async form.** `realpathSync` does not resolve 8.3 short-name aliases, so `CONTRA~1` stays `CONTRA~1` and the resolved-path re-check silently does nothing while still looking correct; `fs.promises.realpath` (`gatedStaticGuard.js:87`) resolves it back to `contracts`. `contracts` is the only gated prefix long enough to get an alias today — a property of the list, not a guarantee.
  - **Auth is Bearer-in-localStorage, so `requireAuth` on a file route breaks `window.open`** — `<img>` and downloads cannot attach an `Authorization` header. Signed URLs are required, not optional; `uid` is an HMAC input, so presenting a different one yields `bad_signature` rather than acting as a claim about identity.
  - **`UPLOADS_SIGNING_SECRET` must fail closed when unset** — `signFileUrl` throws (`signedFileUrl.js:75`), `verifySignedFile` returns `not_configured` (`:107`), and `/sign` surfaces 503. Never a default secret. It is also **required at boot** now (`server/utils/envValidation.js`): the server exits without it, and refuses one shorter than 32 characters, because booting "clean" without it made every private file unreachable with no signal at all.
  - **Back-filled orphans have `uploaded_by: "system"`** (`server/services/uploadsService.js`) and are intentionally admin-only until claimed; `flagUnclaimedPrivateFiles` flags them in the admin listing so they stay discoverable rather than silently locked. That is the contract case: a contract needs two named parties and a system row names none. A chat file adopted by the registry pass is different — chat authorization is message-based, so the thread participants and the uploader can read it.
  - **A blank-party contract is authorized by its creator through `contract_number` provenance.** `documentService.js:621` skips the rating check when either `buyer_id` or `factory_id` is blank, so a draft can exist with both empty. `canAccessContract` (`server/utils/permissions.js:133`) trusts `uploaded_by`, which any caller of `POST /documents/url` can self-assert, so `canUserAccessDocument` additionally requires either a party claim or `uploaded_by == user.id` *and* a `contract_number` (`fileAccessService.js:191-194`). `contract_number` is server-defaulted (`documentService.js:636`), unwritable via `/url` and immutable — which is what makes it safe against pre-existing forged rows. `artifact` was briefly a second marker and was dropped: `PATCH /contracts/:id/artifact` and `/signatures` write it, so a forged row could mint it after creation (`fileAccessService.js:88`).
  - **`.husky/pre-commit`'s test gate reads npm's own exit status** — it used to read grep's, which a red suite could never make non-zero. Do not reintroduce the piped form (`npm test 2>&1 | grep ...` followed by `if [ $? -ne 0 ]`): a red suite still prints `FAIL`/`Tests:`, so grep exits 0 and the gate passes. `set -o pipefail` is not the fix either — husky runs the hook with `sh -e`, and `/bin/sh` is dash on Debian, where pipefail does not exist. `scripts/verify-precommit-gate.sh` extracts the gate from the hook and proves it fails a red suite.

## 10. MainFeed infinite re-render loop ("infinite loading")

- **Problem:** Feed page stuck in perpetual loading spinner; console floods with `WebSocket closed before established` from FloatingAssistant (a side effect). Multiple parallel `GET /api/users/me` requests.
- **Root cause (primary):** Two cascading instability loops:
  1. `loadFeedPage` useCallback depended on `[activeCategory, activeType, token, unique, user?.role, feedConfig, nextCursor, markLoaded]` — any state change (e.g., `user?.role` from `loadUser`, `feedConfig` from config effect) recreated `loadFeedPage`, which re-fired the feed `useEffect`, which changed more state → loop.

  - Previous fixes retained: `markLoaded` in `useCallback`, `nextCursorRef`/`setNextCursorBoth` to decouple cursor state.
- **Fix (auth.js):**
  - `getCurrentUser()` now primes `cachedUser` from `localStorage` via `loadUserFromStorage()` when in-memory cache is cold. Ensures `ProtectedRoute` gets a valid user on first render after page reload, preventing MainFeed unmount.

## 12. Feed page scroll doesn't work inside content area

- **Problem:** Mouse wheel scroll works outside feed panels (sidebar/main) but not inside them. Lenis smooth-scrolls the page when over background, but over the panels nothing scrolls.
- **Root cause (initial):** `data-lenis-prevent={true}` was present unconditionally on both panels. ## 21. Repo hygiene traps (learned the hard way)

- **`.husky/pre-commit` used to run `biome check --write .`** across all 753 files, rewrote ~600 of them, then `git add -u` staged the churn. It now lints only staged files. Do not reintroduce a repo-wide `--write`.
- **`.env` was git-tracked**, so any secret pasted there would be committed. It has been untracked (`git rm --cached .env`); keep secrets in local `.env` only and declare new names in `.env.example`.

## 24. The disk request log stored plaintext passwords and support tokens (Owner)

- **Problem:** `server/middleware/requestCapture.js` wrote every request body, every header and the full URL (with query) to `log/requests.log` with no redaction. That persisted: plaintext passwords and password-reset tokens (auth routes), `x-support-token` buyer bearer tokens (some never expire), and full signed-file URLs (`sig` is an HMAC bearer credential). The in-memory `requestLogger` redacted `authorization`/`cookie` headers, but the disk path skipped it. Signed URLs also leaked into the live log stream via `path: req.originalUrl` (double-mounted for `/api/files`).
- **Fix:** `SENSITIVE_HEADERS` += `x-support-token`; body deep-redaction on `password|token|secret|refresh|authorization|api_key|credential|code` keys and `gtk_sup_` values (JSON bodies via `redactBodyValue`; form-encoded raw bodies via `redactRawBody`; multipart/binary bodies are omitted, never persisted). Both `path` fields now strip query. `errorHandler` truncates the logged error message to 300 chars. `FileAttachmentCard` no longer forwards private `/uploads/...` paths to the client log sink. `log/requests.log` is gitignored.
- **Gotchas:**
  - **The in-memory and disk loggers are two different sanitizers.** Hardening one is not hardening the other; audit every sink separately.
  - **Query strings are credentials.** `/api/files/content?path=&exp=&uid=&sig=` is replayable until expiry. Never log the query, never log a signed URL, never paste one into a transcript.
  - **Non-JSON bodies have no schema to redact against** — treat as opaque and omit, never "log the first 2000 bytes".

## 26. The live read-only gate failed: the shell read the host (Owner)
